# Техническое задание: бэкенд для лендинга Satva Samui

## 1. Общие сведения

**Цель:** сервер для приёма заявок с лендинга, сохранения в БД, отправки на email и просмотра заявок в админке с учётом согласия и расширяемости. Интеграция с CRM **не используется** (поле `amocrm_lead_id` в БД может оставаться для исторических записей).

**Стек:** FastAPI, PostgreSQL, Docker, nginx (reverse proxy + статика). Деплой: Digital Ocean, Ubuntu, Docker.

---

## 2. Архитектура

- **nginx** — обратный прокси к FastAPI, отдача статики (HTML, CSS, JS, img, assets), SSL (TLS).
- **FastAPI** — API (заявки, health, админка), без раздачи статики в проде.
- **PostgreSQL** — хранение заявок, согласий, пользователей админки.
- **Docker** — сервисы: `nginx`, `app` (FastAPI), `postgres`. При необходимости отдельный сервис для отправки email (worker) или отправка из FastAPI.

Статика: в Docker-образе или volume, отдаётся только nginx. FastAPI в проде статику не отдаёт.

---

## 3. Модель данных (расширяемая)

Цель — один механизм заявок с разными типами без потери данных при добавлении новых форм.

- **Таблица `leads` (заявки):**
  - `id` (PK, UUID или bigserial)
  - `type` — тип заявки: `contact` | `procedure_booking` | `package_choice` | … (enum или varchar, индекс)
  - `payload` — JSONB: данные формы (name, phone, package_id, procedure_id, dates, comment и т.д.)
  - `created_at` (timestamptz)
  - `source` — опционально: `landing` | `admin` | …
  - `amocrm_lead_id` — опционально, устаревшее поле (история); для новых заявок не заполняется
  - Уникальный индекс/constraint при необходимости (например, защита от дублей по полям из `payload` + время).

- **Таблица `consents` (согласия с политикой):**
  - `id` (PK)
  - `lead_id` (FK → leads)
  - `ip_address` (inet или varchar)
  - `consent_at` (timestamptz)
  - `policy_version` — строка или ссылка на версию текста политики (например, дата или slug страницы)
  - Опционально: `user_agent`, `referer` для аудита.

- **Таблица `admin_users`:**
  - `id`, `email`, хэш пароля, `role` (admin / viewer при необходимости), `created_at`, `is_active`.

Миграции: Alembic (или аналог). Все изменения схемы — только через миграции, без потери данных.

## 4. API

### 4.1. Публичные эндпоинты

- **POST /api/contact**  
  - Тело: `{ "name": "...", "phone": "...", "consent": true }` (consent обязателен).  
  - Действия: валидация → проверка honeypot/captcha → создание записи в `leads` (type=contact), запись в `consents` (IP, время, версия политики) → сохранение в БД → отправка email → ответ.  
  - Ответ: 200 + `{ "ok": true, "message": "..." }` или 4xx с описанием ошибок валидации.  
  - Rate limit: по лучшим практикам (например, 5–10 req/min с IP на этот эндпоинт).

- **GET /api/health**  
  - Ответ: 200, JSON: `{ "status": "ok", "db": "ok"|"error", "version": "..." }`.  
  - Проверка: подключение к PostgreSQL; при недоступности БД — `db: "error"`, status можно оставить 200 или 503 — зафиксировать единообразно.

### 4.2. Расширение (другие формы)

- Отдельные эндпоинты под новые типы заявок, например:
  - **POST /api/booking** — запись на процедуру (payload: даты, процедура, контакты, согласие).
  - **POST /api/package-request** — выбор пакета (payload: package_id, контакты, согласие).
- Общая логика: валидация → consent в `consents` с привязкой к `lead_id` → запись в `leads` с `type` и `payload` (JSONB) → уведомление на email → ответ.
- Единая таблица `leads` + разные `type` и структура в `payload` позволяют расширять без миграций полей (только новые эндпоинты и опционально новые ключи в JSONB).

### 4.3. Админка (защищённые эндпоинты)

- **POST /api/auth/login** — выдача токена (JWT) по email + пароль; проверка по `admin_users`.
- **GET /api/leads** — список заявок (пагинация, фильтр по `type`, по дате). Доступ только с валидным JWT.
- **GET /api/leads/{id}** — одна заявка с полным payload и связанными согласиями (consent_at, policy_version, ip). Только для авторизованных.

Авторизация: JWT в заголовке `Authorization: Bearer <token>`. Поддержка нескольких админов — через таблицу `admin_users` и роли при необходимости.

## 5. Внешние CRM

- Интеграция с amoCRM и аналогами **не входит** в текущую реализацию. Заявки обрабатываются через БД, email и админку.

## 6. Валидация и безопасность

- **Валидация:** имя (длина, символы), телефон (формат, длина). На бэкенде — обязательно; дублирование правил с фронта по возможности.
- **Согласие:** поле `consent: true` обязательно; при отсутствии — 400. В БД всегда сохранять запись в `consents` (дата, IP, policy_version).
- **Защита от ботов:**
  - Honeypot: скрытое поле в форме (на фронте не заполняется); на бэкенде — отклонять запросы, где honeypot заполнен.
  - Заголовки: проверка `Content-Type: application/json`, при необходимости — базовая проверка `User-Agent`/Referer.
  - Капча: по выбору (reCAPTCHA v3 / hCaptcha / Turnstile). Проверка на бэкенде по токену от капчи перед сохранением заявки.
- **Rate limiting:** на POST-эндпоинты заявок (например, по IP): 5–10 запросов в минуту; на логин — жёстче (например, 5 попыток в 15 минут). Реализация: middleware или nginx (limit_req).

## 6.1. Карта и внешние сервисы

- **Встраивание карты:** на лендинге **не используется** Google Maps Embed API и **не требуется** ключ GCP для отображения карты. В футере — иконка и **внешняя ссылка** на точку Satva Samui в Google Maps (пользователь открывает карту на стороне Google).
- **Секреты:** любые будущие ключи API (карты, аналитика и т.д.) не хранить в коде и репозитории; только в окружении/секретах.

## 7. Email

- При успешном сохранении заявки (contact и в будущем — другие типы) отправлять письмо на заданный адрес (адреса).
- Содержимое: тип заявки, данные из payload (имя, телефон, даты и т.д.), дата заявки. Без паролей и токенов.
- Настройки: SMTP (переменные окружения: host, port, user, password, from). Ошибки отправки логировать и по возможности повторять (очередь или retry), но не падать с 500 пользователю — заявка уже в БД.

---

## 8. Логирование

- **Уровни:** DEBUG (локально), INFO (обычная работа), WARNING (повторные попытки, rate limit), ERROR (исключения, сбой БД/email).
- **Формат:** структурированный JSON в stdout (timestamp, level, message, request_id, path, method, ip, user_id при наличии, error stack при ERROR).
- **Request ID:** на каждый запрос уникальный id, прокидывать в логи и при необходимости в ответ (X-Request-Id).
- **Что логировать:** входящие запросы (method, path, ip), результат (status, duration), ошибки валидации, сбой БД/email, факт создания заявки (без паролей/телефона в открытом виде — маскировать при необходимости по политике).
- Ротация и хранение логов — зона инфраструктуры (Docker logging driver, внешний сборщик логов); в ТЗ зафиксировать только формат и уровень детализации.

---

## 9. Деплой (Docker, Digital Ocean, Ubuntu)

- **Контейнеры:** `nginx`, `app` (FastAPI), `postgres`. Образы: свой для app, официальные для nginx и postgres.
- **Сеть:** только app общается с postgres; снаружи доступен только nginx (80/443).
- **Переменные окружения:** DB URL, SMTP, секрет для JWT, версия приложения, URL фронта для CORS, ключи Cloudflare Turnstile (капча). Все секреты — только из окружения, не в коде и не в репозитории.
- **Volumes:** персистентные данные PostgreSQL; при необходимости — статика для nginx.
- **Health:** оркестратор/мониторинг может проверять `GET /api/health` через nginx (проксирование к app).
