# ТЗ: развитие админ-панели Satva (v2)

**Проект:** satva_landing
**Документ для:** backend/frontend разработчика
**Дата:** 2026-05-29
**Статус:** к реализации

---

## 1. Контекст

Существует админ-панель лендинга отеля Satva:

- **Frontend:** `frontend/samui-ctl-x7f2.html` + `frontend/js/admin.js` + `frontend/css/admin.css`. SPA без фреймворка (ванильный JS, IIFE). Разделы: Заявки, Аналитика, Настройки. Токен хранится в `localStorage` (`satva_admin_token`).
- **Backend:** FastAPI, `server/app/`. JWT-аутентификация (`core/security.py`, `api/deps.py`), bcrypt. PostgreSQL + SQLAlchemy 2.0 + Alembic (последняя миграция `004_lead_status_archive.py`). Email через Resend (`services/email.py`).
- **Модели:** `AdminUser` (есть колонка `role`, дефолт `"admin"`), `Lead` (UUID, `payload` JSONB, `status`, `archived_at`), `Consent`, `AppSetting`.

Цель v2 — добавить управление пользователями с ролями, заметки к заявкам, быстрое редактирование заявок прямо в списке, а также закрыть набор UX- и security-улучшений.

Все новые админ-эндпоинты монтируются с префиксом `/api`, защищены зависимостью аутентификации, и (где указано) проверкой прав. Все даты в БД и API — UTC, ISO 8601.

---

## 2. Нефункциональные требования

- **Совместимость:** не ломать существующий публичный API форм и текущий поток заявок.
- **Миграции:** каждая схема — отдельная Alembic-миграция, нумерация продолжается с `005`. Обязателен рабочий `downgrade`.
- **Безопасность:** любой эндпоинт с данными — только с валидным JWT; эндпоинты управления пользователями — только роль `owner` (см. §3).
- **Стиль:** следовать текущим паттернам репозитория (Pydantic-схемы в `schemas/`, бизнес-логика в `services/`, роутеры в `api/`). Frontend — без новых зависимостей и сборки, в стиле текущего `admin.js`.
- **Экранирование:** любой пользовательский ввод, выводимый в DOM, экранируется (как в текущем `escapeHtml`).

## 3. Эпик 1 — Роли и приглашение пользователей

### 3.1. Модель ролей

Две роли, хранятся в `AdminUser.role`:

| Роль | Заявки (просмотр/статус/архив) | Заметки | Аналитика | Настройки уведомлений | Смена своего пароля | Управление пользователями |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| **owner** | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| **manager** | ✅ | ✅ | ✅ | ❌ | ✅ | ❌ |

- Допустимые значения роли: `owner`, `manager`. Существующих пользователей с `role="admin"` мигрировать в `owner` (миграция данных в §3.6).
- Минимум один активный `owner` в системе должен существовать всегда (см. инварианты §3.5).

### 3.2. Реализация проверки прав (backend)

В `api/deps.py` добавить зависимость-фабрику:

```python
def require_role(*roles: str):
    def _dep(user: AdminUser = Depends(get_current_user)) -> AdminUser:
        if user.role not in roles:
            raise HTTPException(status_code=403, detail="Недостаточно прав")
        return user
    return _dep
```

Эндпоинты управления пользователями и `PUT /api/admin/settings` защищаются `Depends(require_role("owner"))`. Эндпоинты заявок, заметок, аналитики, `GET /api/admin/settings` — доступны обеим ролям (текущая `get_current_user_id`).

`GET /api/auth/me` дополнить полем `role`, чтобы фронт скрывал недоступные разделы/кнопки.

### 3.3. Модель приглашений

Новая таблица `admin_invitations` (миграция `005`):

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | int PK | |
| `email` | varchar(255), unique среди активных | кому приглашение |
| `role` | varchar(32) | `owner` / `manager` |
| `token_hash` | varchar(255) | SHA-256 хэш токена (сырой токен в БД не хранится) |
| `invited_by` | int FK → admin_users.id | кто пригласил |
| `expires_at` | timestamptz | срок жизни (по умолчанию +72 часа) |
| `accepted_at` | timestamptz nullable | когда принято |
| `created_at` | timestamptz | |

### 3.4. Поток приглашения

1. **Owner создаёт приглашение** → `POST /api/admin/users/invite` `{ "email", "role" }`:
   - Проверка: email не принадлежит активному пользователю; нет неистёкшего непринятого приглашения на этот email; роль валидна.
   - Генерируется криптослучайный токен (`secrets.token_urlsafe(32)`), в БД пишется только его SHA-256.
   - Отправляется письмо (Resend, по образцу `services/email.py`) со ссылкой:
     `https://satvasamui.com/<admin-path>?invite=<raw_token>`
     (использовать обфусцированный путь админки; вынести его в конфиг.)
   - Ответ: данные приглашения **без** сырого токена.
2. **Приглашённый открывает ссылку** → фронт показывает экран «Принятие приглашения»: поля email (предзаполнен и заблокирован, приходит из проверки токена), пароль, подтверждение пароля.
   - `GET /api/admin/invitations/{raw_token}` → валидирует токен (хэш совпал, не истёк, не принят), возвращает `{ email, role }` или 404/410.
   - `POST /api/admin/invitations/{raw_token}/accept` `{ "password" }` (min 8) → создаёт `AdminUser` с указанной ролью, помечает приглашение `accepted_at`, возвращает JWT (сразу логинит).
3. **Повторная отправка / отзыв:** `POST /api/admin/users/invite` с тем же email пересоздаёт приглашение (старое инвалидируется); `DELETE /api/admin/invitations/{id}` отзывает непринятое.

### 3.5. Управление пользователями (API)

Все — `Depends(require_role("owner"))`:

- `GET /api/admin/users` → список `{ id, email, role, is_active, created_at }`.
- `GET /api/admin/invitations` → список непринятых приглашений `{ id, email, role, expires_at, invited_by }`.
- `PATCH /api/admin/users/{id}` `{ role?, is_active? }` → сменить роль / деактивировать.
- `DELETE /api/admin/users/{id}` → деактивация (мягкое удаление: `is_active=false`; физически не удалять ради ссылок в заметках/аудите).

**Инварианты (валидация на сервере, ошибка 400):**
- Нельзя понизить роль/деактивировать последнего активного `owner`.
- Нельзя деактивировать самого себя.
- Деактивированный пользователь немедленно теряет доступ (см. §6 — отзыв токенов).

### 3.6. Миграция данных

В миграции `005`: `UPDATE admin_users SET role='owner' WHERE role='admin'`. В `downgrade` — обратно в `admin`.

### 3.7. UI: новый раздел «Пользователи»

- Пункт меню «Пользователи» в сайдбаре (`samui-ctl-x7f2.html`), **видим только при `role==="owner"`** (после `loadMe()`).
- Таблица пользователей: email, роль (селект для смены), статус (активен/выкл), дата. Кнопка «Деактивировать».
- Блок «Пригласить»: поле email + селект роли + кнопка «Отправить приглашение». Ниже — список ожидающих приглашений с кнопками «Отправить повторно» / «Отозвать».
- Экран «Принятие приглашения» — отдельный блок (по аналогии с `admin-login`), показывается если в URL есть `?invite=...` (до проверки токена прочих блоков не рендерить).
- Кнопки/разделы, недоступные роли `manager`, скрываются на фронте **и** защищены на бэке (фронт — только UX, бэк — источник правды).

### 3.8. Критерии приёмки (Эпик 1)

- Owner приглашает по email → письмо приходит → по ссылке создаётся manager → manager входит и видит Заявки/Аналитику, но не видит Настройки и Пользователей.
- Manager, обратившись к `POST /api/admin/users/invite` напрямую, получает 403.
- Попытка деактивировать единственного owner → 400 с понятным сообщением.
- Истёкший/использованный invite-токен → 410, аккаунт не создаётся.

## 4. Эпик 2 — Заметки к заявкам

### 4.1. Модель

Новая таблица `lead_notes` (миграция `006`):

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | int PK | |
| `lead_id` | UUID FK → leads.id (ON DELETE CASCADE) | |
| `author_id` | int FK → admin_users.id | автор |
| `body` | text | текст заметки |
| `created_at` | timestamptz | |
| `updated_at` | timestamptz nullable | |

Связь `Lead.notes` (relationship, `cascade="all, delete-orphan"`).

### 4.2. API (обе роли)

- `GET /api/leads/{lead_id}/notes` → список заметок (новые сверху) с `{ id, body, created_at, updated_at, author: { id, email } }`.
- `POST /api/leads/{lead_id}/notes` `{ "body" }` → создать (автор = текущий пользователь). Пустой/пробельный body → 400.
- `PATCH /api/leads/{lead_id}/notes/{note_id}` `{ "body" }` → редактировать. Разрешено автору заметки или роли `owner`.
- `DELETE /api/leads/{lead_id}/notes/{note_id}` → удалить. Те же права, что на PATCH.

### 4.3. UI

В карточке заявки (`#admin-lead-detail`) добавить панель **«Заметки»**: поле ввода + кнопка «Добавить», ниже — лента заметок с автором и датой, у своих/как owner — кнопки «Изменить»/«Удалить». Заметки также используются в попапе быстрого редактирования (§5) в свёрнутом виде: счётчик + последняя заметка + поле быстрого добавления.

### 4.4. Критерии приёмки

- Manager добавляет заметку → она видна другому пользователю с автором и временем.
- Manager не может отредактировать чужую заметку (403); owner — может.
- Удаление заявки каскадно удаляет заметки.

## 5. Эпик 3 — Быстрое редактирование заявки в списке (попап)

### 5.1. Поведение

В таблице заявок (`#admin-leads-tbody`) клик по строке (или по кнопке «Быстро») открывает **модальное окно** поверх списка, без перехода на отдельный экран:

- Заголовок: тип + имя + телефон (`tel:` ссылка).
- **Статус** — селект, изменение сразу шлёт `PATCH /api/leads/{id}` `{ status }` (как сейчас в карточке), с инлайн-индикатором «Сохранено».
- **Архив/Восстановить** — кнопка, `PATCH { archived }`.
- **Заметки** — счётчик + последняя заметка + поле «быстро добавить заметку» (`POST .../notes`).
- Кнопка «Открыть полную карточку» → текущий экран `#admin-lead-detail`.
- Закрытие: крестик, клик по затемнению, `Esc`.

После успешного изменения строка в таблице обновляется (статус-бейдж/состояние архива) без полной перезагрузки списка; при изменении архивности — строка убирается из текущей вкладки.

### 5.2. Реализация

- Backend изменений не требует — переиспользуются `PATCH /api/leads/{id}` и notes-API (§4).
- Frontend: добавить разметку модалки в `samui-ctl-x7f2.html` (скрыта по умолчанию), стили в `admin.css` (в проекте уже есть стиль модалок на лендинге — следовать ему), логику в `admin.js`: `openQuickEdit(id)`, фокус-trap, `aria-modal="true"`, возврат фокуса на строку при закрытии.
- Кнопка «Подробнее» в строке сохраняется (открывает полную карточку); основной клик по строке — попап.

### 5.3. Критерии приёмки

- Смена статуса в попапе отражается в строке списка и в БД без перезагрузки страницы.
- Доступность: попап открывается/закрывается с клавиатуры, фокус не уходит за пределы, `Esc` закрывает.
- На мобильном (≤480px) попап занимает экран корректно, прокручивается.

## 6. Эпик 4 — Безопасность

### 6.1. Отзыв токенов (token versioning)

Проблема: JWT в `localStorage` нельзя отозвать; после смены пароля/деактивации старые токены валидны.

- Добавить `AdminUser.token_version int default 0` (миграция).
- В JWT-claims писать `tv` = текущая `token_version`; в `get_current_user` сверять `tv` из токена с БД — при несовпадении 401.
- Инкрементировать `token_version` при: смене пароля (`change-password`), деактивации пользователя, смене роли. Это мгновенно «разлогинивает» все сессии пользователя.

### 6.2. Прочее

- **`JWT_SECRET`**: убедиться, что в проде задаётся через env (не дефолт `change-me-in-production`); при старте с дефолтным секретом и `DEBUG=false` — падать с явной ошибкой.
- **Аудит-лог**: таблица `admin_audit_log` (`id, actor_id, action, target_type, target_id, meta JSONB, created_at`). Логировать: вход, смена статуса заявки, архив/восстановление, приглашение/деактивация пользователя, смена настроек. Раздел просмотра лога — для `owner` (можно вынести в отдельную задачу, но таблицу и запись завести сразу).
- **Индексация админки**: отдавать заголовок `X-Robots-Tag: noindex, nofollow` для админ-страницы (nginx, см. `nginx.conf`) и добавить `Disallow` в `robots.txt`. Путь админки вынести в конфиг/env, не хардкодить в нескольких местах.
- **datetime**: заменить устаревший `datetime.utcnow()` на `datetime.now(timezone.utc)` в новом и (по возможности) существующем коде (`security.py`, `leads.py`).

### 6.3. Критерии приёмки

- После смены пароля старый токен немедленно отдаёт 401.
- Деактивированный пользователь с действующим токеном получает 401 на следующем запросе.
- Запрос к админ-странице возвращает `X-Robots-Tag: noindex`.

## 7. Эпик 5 — UX-улучшения списка и аналитики

Приоритет средний; можно как отдельные задачи.

1. **Поиск** по имени/телефону/email: параметр `q` в `GET /api/leads`, поиск по `payload->>'name'`, `payload->>'phone'`, `payload->>'email'` (ILIKE). Поле поиска в тулбаре фильтров.
2. **Общее число и пагинация**: возвращать总 количество (заголовок `X-Total-Count` или поле `total` в обёртке ответа). Фронт показывает «N–M из T» и корректно блокирует «Вперёд» на последней странице (сейчас при ровно 20 записях кнопка ведёт на пустую страницу).
3. **Кликабельные контакты**: телефон → `tel:`, email → `mailto:` в таблице, попапе и карточке.
4. **Пресеты периода**: кнопки «Сегодня / 7 дней / 30 дней» рядом с ручным выбором дат.
5. **Состояние фильтров в URL** (query-параметры): при навигации между разделами и `refresh` фильтры/страница сохраняются; ссылку с фильтром можно расшарить.
6. **Бейдж новых заявок** в пункте меню «Заявки» — количество `status=new` в активных (лёгкий эндпоинт-счётчик или из `X-Total-Count` с фильтром).
7. **Экспорт CSV**: `GET /api/leads/export?<те же фильтры>` → `text/csv` (дата, тип, статус, имя, телефон, email, источник). Только авторизованные.
8. **Аналитика — конверсия**: на экране аналитики показать число заявок за период (из БД) и конверсию «заявки / визиты», плюс простой график динамики заявок по дням (можно без внешних библиотек — inline SVG/CSS-бары).

Критерии приёмки — по каждому пункту: функция работает на десктопе и мобильном, не ломает существующие фильтры, данные совпадают с БД.

## 9. Сводка новых эндпоинтов

| Метод | Путь | Права | Назначение |
|------|------|-------|-----------|
| GET | `/api/auth/me` | любой | + поле `role` (доработка) |
| GET | `/api/admin/users` | owner | список пользователей |
| PATCH | `/api/admin/users/{id}` | owner | роль / активность |
| DELETE | `/api/admin/users/{id}` | owner | деактивация |
| POST | `/api/admin/users/invite` | owner | создать/переслать приглашение |
| GET | `/api/admin/invitations` | owner | список приглашений |
| DELETE | `/api/admin/invitations/{id}` | owner | отозвать |
| GET | `/api/admin/invitations/{token}` | публичный | проверить приглашение |
| POST | `/api/admin/invitations/{token}/accept` | публичный | принять, создать аккаунт |
| GET | `/api/leads/{id}/notes` | любой | заметки |
| POST | `/api/leads/{id}/notes` | любой | создать заметку |
| PATCH | `/api/leads/{id}/notes/{nid}` | автор/owner | изменить |
| DELETE | `/api/leads/{id}/notes/{nid}` | автор/owner | удалить |
| GET | `/api/leads` | любой | + `q`, `X-Total-Count` (доработка) |
| GET | `/api/leads/export` | любой | CSV |

«Любой» = любой активный авторизованный пользователь (owner или manager).

## 10. Глобальные критерии готовности (Definition of Done)

- Все миграции применяются и откатываются без ошибок.
- Права проверяются на бэке (не только скрытием в UI); manager не может обойти ограничения прямыми запросами.
- Нет регрессий в публичных формах и текущем потоке заявок.
- Новый UI работает на десктопе и мобильном, проходит базовую проверку доступности (клавиатура, aria, фокус в модалках).
- Секреты — из env; админ-страница `noindex`.
- Короткое README/раздел в `DEPLOY.md` про новые env-переменные (путь админки, срок жизни приглашения) и про создание первого owner.
